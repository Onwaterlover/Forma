# Architecture

A single Next.js 16 application (App Router, TypeScript strict) on Postgres: **Supabase** in the cloud (deployed on Vercel), or the embedded **PGlite** (Postgres compiled to WebAssembly, stored in a local folder) when no `DATABASE_URL` is set. Same schema and queries in both.

```
Browser / installed PWA
  │  HTML (server components), server actions, small JSON routes
  ▼
Next.js server (Node ≥ 22.13)
  ├─ src/app/**            pages, server actions (src/app/actions), JSON routes (src/app/api)
  ├─ src/lib/auth.ts       sessions, password hashing, invites
  ├─ src/lib/data.ts       the only module that touches the DB; every query is scoped by user id
  ├─ src/lib/off.ts        Open Food Facts client (rate limited + cached)
  ├─ src/engine/**         training engine — pure TypeScript, no I/O, shared by server and browser
  ├─ src/nutrition/**      nutrition maths, barcode helpers, OFF mapping, energy/trend models — pure
  └─ src/import/**         deterministic plan import parser — pure
  ▼
Supabase Postgres (DATABASE_URL, via postgres.js)  ·  or  ·  DATA_DIR/pg (PGlite, local)
```

## Key decisions

| Decision | Why |
|---|---|
| **Postgres (Supabase) + PGlite locally** | Vercel has no persistent disk, so the cloud uses Supabase Postgres (free tier, EU region). Locally and in tests the same SQL runs on PGlite, so no database server is needed. `src/lib/db.ts` is a tiny async adapter (`?` placeholders → `$n`). Row Level Security is enabled on every table with no policies: Supabase's public API keys can read nothing; the server connects as the owner and scopes every query by user. |
| **Raw SQL + typed functions instead of an ORM** | Small schema, explicit queries, and no extra dependency or codegen. Migrations are append-only (`src/lib/migrations.ts`) and run automatically at start-up under an advisory lock (safe with concurrent serverless instances). |
| **Pure engine modules** | The generator, validator, progression and nutrition maths are deterministic and unit-tested. The same code runs in the browser for live validation, swaps, location changes and "shorten my workout" without a round-trip. |
| **Server actions for mutations, JSON routes only where needed** | Workout autosave/offline sync (`PUT /api/workouts/:id`), food search, barcode lookup and data export. |
| **Session cookies** | Opaque random token in an httpOnly, SameSite=Lax cookie. Only its SHA-256 is stored, and sessions expire after 30 days. Passwords use scrypt. |
| **Invite-only registration** | The first account becomes admin. Invites are stored hashed and are single-use with a 14-day expiry. |
| **i18n** | Polish is the source dictionary (`src/i18n/pl.ts`). English and German must match its shape (enforced by `tsc`). Engine messages are codes with parameters and are rendered per locale. |
| **Design system** | Tailwind v4 with CSS tokens (`src/app/globals.css`): warm stone neutrals plus a single sage accent, with light and dark themes and system fonts. Components live in `src/components`. |

## Security model

- Authorization happens server-side in every data function (`WHERE user_id = ?`). Hiding UI is never the security boundary.
- Server actions are protected by Next's Origin/Host check. JSON routes that write use `sameOrigin()` (`src/lib/http.ts`). For reverse proxies, see `ALLOWED_ORIGINS`.
- Inputs from the browser are validated with zod (`src/lib/schemas.ts`, inside actions). Nutrient data from external sources is sanitised (impossible values become `null`).
- The admin can create invites but has no screen or query that reads other users' health or food data.
- The service worker never caches `/api/*` and clears cached pages when the login page is shown.
- No telemetry. The only outbound calls are Open Food Facts lookups/searches made on the user's explicit action and, if the admin configured it and the user switched it on, the Anthropic API for the assistant (see [integrations](integrations.md#optional-ai-assistant-claude)).

## Offline behaviour

- The workout logger writes every change to `localStorage` first and then debounces a `PUT` to the server. If the network fails, it shows an "offline" badge and retries on the browser's `online` event.
- Workout ids are generated by the client, so retries are idempotent. The server ignores payloads older than what it has (`clientUpdatedAt`), so an old offline copy never overwrites newer data.
- The service worker caches the app shell and open workout pages so a short dropout doesn't break the screen. Product search and remote lookups are not available offline. Already-saved foods work once online again.

## Expansion path

- More users or remote hosting: swap SQLite for PostgreSQL behind `data.ts`, and add HTTPS and a reverse proxy.
- Progress photos: resized in the browser (max 1600 px, JPEG, EXIF/GPS removed), stored in the `progress_photos` table and served only through `/api/photos/:id` after an owner check. At ~150–300 KB each, a weekly set of three for five people is roughly 150 MB a year of the 500 MB free database.
- AI assistant: `src/lib/assistant.ts` sends only the data a section needs. Changes are stored as `ai_suggestions` rows and applied only when the user taps Apply, through the normal server actions.
